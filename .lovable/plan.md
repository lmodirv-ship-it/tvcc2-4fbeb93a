# سجل نطاقات ‎.HN‎ الخاص وربطه بالسيرفرات المحلية

إنشاء "سجل نطاقات" داخلي داخل المنصة يسمح بحجز أسماء تنتهي بـ ‎.hn‎ مثل `www.example.hn`، ثم توجيهها إلى سيرفر محلي ومنفذ محدد. هذه نطاقات خاصة تعمل داخل شبكتك (LAN/VPN) وليست نطاقات عالمية — يتم حلّها عبر خادم DNS محلي تديره المنصة على السيرفر.

## كيف يعمل

```text
حجز الاسم         ->  ربطه بسيرفر + منفذ   ->  نشر إلى السيرفر        ->  الوصول
example.hn            server #1 : 3000        منطقة DNS + Nginx        http://www.example.hn
```

1. **الحجز:** المستخدم يكتب `example` فيصبح النطاق `example.hn` (مع `www.example.hn` تلقائياً). تحقق من التنسيق ومن عدم تكرار الاسم على مستوى المنصة كلها.
2. **الربط:** اختيار سيرفر من قائمة سيرفراتك + عنوان IP داخلي + منفذ الخدمة، أو ربطه بموقع موجود في صفحة المواقع.
3. **النشر:** زر "نشر" يرسل أمراً للوكيل (Agent) على السيرفر لكتابة سجل DNS محلي (dnsmasq/CoreDNS) وvhost في Nginx يوجّه النطاق إلى المنفذ، ثم إعادة تحميل الخدمتين.
4. **الاستخدام:** أي جهاز في الشبكة يضبط DNS على IP السيرفر يفتح `http://www.example.hn` مباشرة. المنصة تعرض إرشادات الضبط لكل نظام (ويندوز/ماك/لينكس/أندرويد/راوتر).

## الصفحة الجديدة: "نطاقات ‎.HN‎"

- جدول بكل النطاقات المحجوزة: الاسم، السيرفر، IP، المنفذ، حالة النشر (محجوز / منشور / خطأ)، آخر تحديث.
- نموذج حجز سريع مع معاينة مباشرة للاسم النهائي `www.<name>.hn`.
- أزرار لكل نطاق: نشر، إعادة نشر، فحص (هل يستجيب الاسم فعلاً من السيرفر؟)، تعديل الربط، حذف (يزيل السجل من السيرفر أيضاً).
- إضافة سجلات فرعية اختيارية: `api.example.hn`, `db.example.hn` بمنافذ مختلفة.
- بطاقة إرشادات "كيف أجعل أجهزتي ترى نطاقات ‎.hn‎" مع IP خادم DNS جاهز للنسخ.
- شارة "نطاق ‎.HN‎ عام" — النطاق لا يبقى محلياً فقط: يُنشر أيضاً إلى الإنترنت عبر البوابة العامة (VPS + نفق آمن) فيصبح `www.example.hn` قابلاً للوصول من خارج الشبكة عبر HTTPS، مع بقاء المسار الداخلي عبر DNS المحلي للسرعة. ولكل نطاق زر **منح شهادة HN.RLS** (بالإضافة إلى شهادة HN-TLS للتشفير) تُصدر تلقائياً بعد التحقق من الملكية وتُسجَّل في `hn_certificates`.

## نقاط مهمة

- ‎.hn‎ هو في الأصل امتداد دولة (هندوراس)، لذلك هذه النطاقات تعمل **داخل شبكتك فقط** ولن تكون قابلة للوصول من الإنترنت العام. سيظهر هذا التنبيه بوضوح في الصفحة.
- الشهادات: HTTP يعمل مباشرة؛ HTTPS يتطلب شهادة داخلية (CA خاص) — سيتم توليد شهادة موقّعة ذاتياً اختيارياً في مرحلة لاحقة.

## استضافة مدفوعة: نطاق + تخزين + قاعدة بيانات

كل من ينشئ موقعاً على المنصة يحصل على باقة استضافة: نطاقات ‎.hn‎ (أو نطاقه الخاص)، مساحة تخزين، واتصال بقاعدة بيانات Supabase الذاتية.

**تصحيح جوهري:** Supabase ذاتي الاستضافة يعمل كمشروع واحد؛ لا يمكن إنشاء "مشروع مستقل" لكل مشترك إلا بتشغيل Stack/حاويات منفصلة. لذلك العزل يتدرّج: مستأجر (tenant) داخل قاعدة مشتركة → schema ودور معزولان → Stack مستقل.

لا وعد بـ PITR أو Failover قبل تجهيز خادم ثانٍ — تُعرض كـ "قريباً" وليست ضمن التزامات الباقات الحالية.

### البنية الصحيحة للاتصال

```text
المواقع والعملاء
   -> بوابة HTTPS عامة على VPS (https://db.hn-groupe.org)
   -> نفق آمن TVCC / WireGuard
   -> Nawat Hosting API
   -> Supabase الداخلي 192.168.100.66 (المنفذ لا يُكشف أبداً)
   -> HN-Cloud: نسخ مشفّرة
```

- المواقع خارج الشبكة لا تصل إلى `192.168.100.66` مباشرة؛ الوصول عبر Reverse Proxy عام مع HTTPS ودعم WebSocket (Realtime).
- المنفذ 8000 لا يُنشر على الإنترنت إطلاقاً.

### ما يحصل عليه المشترك عند التفعيل

1. مساحة تخزين باسم الموقع على السيرفر (`/var/www/<domain>`) مع حصة (quota) تُفرض فعلياً، ومجلد/ملف تهيئة خاص بكل نطاق.
2. هوية مستأجر: `tenant_id` + سياسات RLS + bucket منفصل في تخزين Supabase (سياسات مستقلة على `storage.objects` لكل مشترك وbucket). في Pro: schema ودور معزولان. في Business: Stack مستقل.
3. تسليم متغيرات البيئة للموقع: عنوان البوابة العامة + **المفتاح العام فقط**. `service_role` لا يُمنح لأي موقع إطلاقاً ويبقى داخل خادم Nawat لأنه يتجاوز RLS.
4. نشر النطاقات ‎.hn‎ وربطها بالمنافذ، وتفعيل النسخ الاحتياطي حسب الباقة.

### السرية وحماية البيانات

- عزل متدرّج: tenant_id + RLS (Starter/Basic)، schema ودور (Pro)، Stack مستقل (Business+).
- سياسات RLS مستقلة على `storage.objects` لكل bucket ومستأجر.
- كل المفاتيح السرية تُخزَّن في خزنة AES-256-GCM ولا تُرسل إلى المتصفح؛ المفتاح العام فقط يصل للموقع.
- سجل تدقيق لكل عملية (إنشاء/ترقية/حذف)، ومراقبة استهلاك التخزين والنقل مع منع الرفع عند تجاوز الحصة.
- عنوان الخادم الداخلي لا يظهر في أي واجهة عامة.

### الصفحة الرسمية

- قسم "خدماتنا": استضافة، تخزين، Supabase، نطاقات ‎.HN‎، نسخ احتياطي وحماية.
- بطاقات الباقات الخمس مع جدول مقارنة كامل، ومبدّل شهري/سنوي بخصم سنوي.
- حاسبة استهلاك وإضافات (تخزين/نقل/نطاقات).
- صفحات مستقلة: `/pricing`، `/security` (الأمن والخصوصية وملكية البيانات)، `/status` (حالة الخوادم)، `/terms` (شروط الاستخدام وسياسة الاسترجاع).
- زر "ابدأ بـ 2$" ينشئ الاشتراك ثم يبدأ التزويد تلقائياً.

## التفاصيل التقنية


- جدول جديد `public.hn_domains`: `owner_id`, `name` (بدون اللاحقة، فريد عالمياً), `fqdn`, `server_id` (FK إلى `servers`), `website_id` (اختياري), `target_ip`, `target_port`, `records jsonb` (سجلات فرعية), `status` (`reserved|published|error`), `last_published_at`, `last_error`, `created_at`, `updated_at` + GRANT للأدوار + تفعيل RLS + سياسات مقصورة على المالك/‏`system_owner` عبر `can_manage(owner_id)` + trigger `touch_updated_at`.
- `src/lib/hn-domains.server.ts`: توليد `fqdn`، التحقق من الاسم (`^[a-z0-9]([a-z0-9-]{1,61}[a-z0-9])?$`)، بناء ملف منطقة dnsmasq (`address=/example.hn/<ip>`) وvhost Nginx عبر `buildProxyConf` الموجود في `mesh.server.ts`.
- `src/lib/hn-domains.functions.ts` بدوال محمية بـ `requireSupabaseAuth`: `listHnDomains`, `reserveHnDomain`, `bindHnDomain`, `publishHnDomain`, `checkHnDomain`, `deleteHnDomain` — النشر يمر عبر آلية `server_commands` الحالية نفسها المستخدمة في المنافذ وإعادة التوجيه.
- تحديث `src/lib/agent-script.ts` (إصدار 2.8.0) بإجراءات: `hn_dns_install` (تثبيت/تهيئة dnsmasq مرة واحدة)، `hn_domain_publish`، `hn_domain_remove` — مع حراسة الاسم عبر `isSafeDomain` قبل أي كتابة ملف.
- صفحة `src/routes/_authenticated/hn-domains.tsx` + عنصر في `AppSidebar` بجانب "مدير النطاقات"، مع `head()` خاص بها.
- أداة MCP `list_hn_domains` لقراءة النطاقات الداخلية من المساعدات الذكية.
- جداول الاستضافة الجديدة: `hosting_plans` (اسم، سعر شهري/سنوي، تخزين GB، عدد المواقع، عدد نطاقات ‎.hn‎، النقل الشهري GB، نوع عزل القاعدة `shared|schema|stack`، حصة القاعدة MB، مميزات jsonb، ترتيب، مرئية)، `hosting_subscriptions` (owner_id, website_id, plan_id, status, billing_cycle, current_period_end, addons jsonb)، `hosting_tenants` (owner_id, subscription_id, tenant_id, isolation, schema_name, db_role, bucket_name, status)، `storage_quotas` (owner_id, website_id, limit_bytes, used_bytes, transfer_bytes, updated_at) — كلها مع GRANT + RLS بسياسات `can_manage(owner_id)`، وقراءة عامة للباقات فقط (`hosting_plans` بسياسة `TO anon` على الأعمدة العامة) لعرض التسعير.
- الباقات تُدرج كصفوف حقيقية في الترحيل (migration) لتظهر صفحة التسعير مباشرة.
- `src/lib/hosting.server.ts` + `src/lib/hosting.functions.ts` (محمية بـ `requireSupabaseAuth`): `subscribePlan`, `provisionHosting`, `getUsage`, `upgradePlan`, `cancelPlan` — الاتصال بـ Supabase الذاتي عبر أسرار خادم `SELFHOST_SUPABASE_URL` (البوابة العامة) و`SELFHOST_SUPABASE_SERVICE_KEY` تُقرأ داخل الـ handler فقط ولا تُعاد أبداً للعميل.

- صفحات: `/pricing` و`/security` و`/status` و`/terms` عامة (SSR + head خاص + JSON-LD للمنتجات)، وقسم تسعير في `src/routes/index.tsx`، و`/_authenticated/hosting` لإدارة الاشتراك والاستهلاك والترقية.
- الدفع: يبدأ يدوياً/فاتورة داخلية عبر جدول الاشتراكات الحالي، مع تفعيل الدفع الآلي في مرحلة لاحقة دون تغيير المخطط.
