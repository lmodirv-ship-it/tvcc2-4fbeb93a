# تفعيل الأزرار فعلياً + تقرير فحص شامل

## ما تم التحقق منه الآن (من قاعدة البيانات)

- المزوّد الوحيد المسجَّل: «نماذج hn» نوعه `server` وحالته `error`، وعنوانه `http://127.0.0.1:11434`.
- 7 نماذج (qwen3, deepseek-r1, qwen2.5-coder...) كلها بنفس العنوان `127.0.0.1:11434`.
- جدول `ai_messages` فيه رسالتان من المستخدم فقط («سلام») ولا يوجد أي رد مساعد.
- السيرفر `hn` مسجَّل بعنوان LAN `192.168.100.83` وبدون `public_ip`.

**السبب الجذري لعدم رد النماذج:** دالة المحادثة تعمل على خادم Lovable السحابي، وتحاول الاتصال بـ `127.0.0.1:11434` — وهذا عنوان داخل حاسوبك/سيرفرك ولا يمكن للسحابة الوصول إليه إطلاقاً. لذلك الطلب يفشل قبل أن يصل إلى النموذج.

## ما سأنفّذه

### 1. تشغيل المحادثة فعلياً (3 مسارات)

- **نماذج على جهازك/الشبكة المحلية:** أي نموذج عنوانه `127.0.0.1` أو `localhost` أو نطاق شبكة خاصة يُعامَل تلقائياً كنموذج محلي، فيُستدعى من متصفحك مباشرة (متصفحك داخل الشبكة يصل إليه). حالياً هذا يحدث فقط للنوع `local`، وسأوسّعه بالكشف عن العنوان.
- **تشغيل الأدوات مع النماذج المحلية:** حالياً النماذج المحلية «بدون أدوات». سأضيف حلقة أدوات في المتصفح: النموذج يطلب أداة → المتصفح ينادي دالة خادم موقّعة لتنفيذ الأداة (قراءة المواقع/السيرفرات/الإحصاءات) → تُعاد النتيجة للنموذج. وتُحفظ الرسائل في `ai_conversations` / `ai_messages` كبقية المحادثات.
- **تمرير عبر وكيل السيرفر (relay):** للنماذج الموجودة على VPS غير متاح للإنترنت، يُرسَل الطلب كأمر `ai_infer` عبر آلية `server_commands` الموجودة، ويردّه الوكيل في الـ heartbeat.
- **مزوّد سحابي جاهز:** زر «تفعيل نماذج Lovable AI» في `/ai-connect` ينشئ المزوّد ونماذجه تلقائياً، ليتوفّر نموذج يعمل دائماً حتى بدون Ollama.
- رسائل خطأ واضحة بدل الصمت (تعذّر الوصول للنموذج / المزوّد غير متصل / رصيد غير كافٍ).

### 2. ربط النطاق والـ DNS فعلياً

- صفحة `editor/dns` حالياً تحفظ القيم في `website_settings` فقط ولا تنفّذ شيئاً. سأحوّلها إلى إجراء حقيقي:
  - «فحص DNS» يستدعي فحص فعلي (سجلات A/CNAME/TXT عبر DNS-over-HTTPS) ويعرض القيم الحالية والمطلوبة.
  - «التحقق من الملكية» يستخدم مسار `verifyDns` / `checkDomainOwnership` الموجود، ثم يصدر شهادة HN.RLS ويسجّل المشروع، مع عرض حالة كل خطوة.
  - عرض تعليمات السجل المطلوب (اسم/نوع/قيمة) قابلة للنسخ داخل صفحة الموقع.
- في `/websites`: بعد إضافة موقع يُعرض كود التحقق وسجل DNS المطلوب وزر «تحقّق الآن» يعطي نتيجة حقيقية (نجاح/سبب الفشل)، وليس مجرد حفظ.

### 3. جرد كل الأزرار غير العاملة

مراجعة كل صفحة (المواقع، النطاقات، SSL، السيرفرات، النسخ الاحتياطي، الخزنة، الوظائف، المراقبة، الإشعارات، Core Hub، المدفوعات، استوديو الفيديو، المحرر بكل تبويباته، APK، القوالب، المجموعات، الخدمات، التقارير) وتصنيف كل زر:
- يعمل ✔
- يحفظ فقط بدون أثر حقيقي → يُربَط بمنطق فعلي
- بلا وظيفة → يُفعَّل أو يُزال

الأولوية للأزرار التي يتوقع منها المستخدم أثراً خارجياً (فحص، تحقق، تنفيذ، نسخ احتياطي، إرسال إشعار).

### 4. تقرير مفصّل بالتجربة

بعد التنفيذ أشغّل متصفحاً حقيقياً على المنصة وأسجّل الدخول، وأجرّب صفحة صفحة، وأسلّم تقريراً يحتوي:
- جدول: الصفحة / الزر / ما جرّبته / النتيجة قبل وبعد.
- لقطات شاشة للتجارب الأساسية (المحادثة تردّ، إضافة موقع، فحص DNS والتحقق، فحص حالة موقع، أمر سيرفر بوضع محاكاة).
- قائمة بما لا يمكن إثباته من السحابة (مثل Ollama داخل شبكتك) مع طريقة اختباره من جهازك.

## تفاصيل تقنية

- كشف «محلي»: تحليل `endpoint_url`/`base_url` لـ `127.0.0.1`, `localhost`, `10.x`, `192.168.x`, `172.16-31.x` → مسار المتصفح.
- حلقة الأدوات في المتصفح تستدعي دالة خادم جديدة `runAiTool` محمية بـ `requireSupabaseAuth`، تعيد استخدام تعريفات `AI_TOOLS` في `src/lib/ai-tools.server.ts` دون تكرارها، مع احترام مفتاح «السماح بالتعديل».
- فحص DNS من الخادم عبر DNS-over-HTTPS (لا يوجد `dns` module في بيئة الحافة).
- لا تغييرات في المخطط إلا عند الحاجة لتخزين نتائج فحص DNS؛ وإن لزم فستكون داخل `website_settings` الموجود.
