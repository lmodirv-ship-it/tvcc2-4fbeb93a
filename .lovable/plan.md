# تطوير الصفحات الحالية + تهجير قواعد بيانات 240+ موقعاً

الهدف: تطوير الصفحات الموجودة (مع إمكانية إضافة صفحات جديدة عند الحاجة) لتصبح إدارة المواقع وقواعد البيانات والسيرفرات والتخزين مبنية على «من يملك ماذا» و«ما المرتبط بماذا»، ثم تجهيز المنصة لاستقبال وتهجير قواعد بيانات أكثر من 240 موقعاً. لا حذف لأي جدول أو بيانات.

## 1) تطوير صفحة «المستخدمون والفريق» (`/users`)

- **مصفوفة الصلاحيات** تصبح واضحة: أدوار × صلاحيات مجمّعة (المواقع، البنية التحتية، الوكيل، قواعد البيانات، الأمان، الفريق، الأعمال).
- **تبويب «صلاحيات لكل موقع»**: اختيار موقع ثم من يصل إليه ومستواه (قراءة / تحرير / إدارة).
- **تبويب «صلاحيات السيرفرات وقواعد البيانات»**: من يشغّل أوامر الوكيل، يقرأ، يكتب، يغيّر البنية.
- تأكيد لكل تغيير + تسجيل في سجل النشاط، وحماية حساب المالك الدائم كما هي.

## 2) تطوير صفحة «خريطة العلاقات» (`/topology`)

- سلسلة كل موقع: `الموقع (S######) ← قاعدة البيانات ← السيرفر ← الوكلاء ← النطاق/الشهادة ← التخزين ← النسخ ← التنبيهات`.
- جدول شامل لكل المواقع بأعمدة ✓/✗ (قاعدة / سيرفر / وكيل / نطاق / تخزين / نسخ)، تصفية «الناقص فقط»، تصدير CSV.
- زر «ربط الآن» للروابط الناقصة يحفظ الربط مباشرة، وعدّادات للمكتمل مقابل الناقص.

## 3) تطوير صفحة «المواقع» (`/websites`)

- عمود «الارتباط» يلخّص قاعدة/سيرفر/نطاق/نسخ لكل موقع، مع الانتقال إلى خريطة العلاقات مع اختيار مسبق.

## 4) تهجير قواعد البيانات على نطاق واسع (240+ موقعاً)

يُبنى داخل **مركز قواعد البيانات** في قسمَي «الاستيراد والتصدير» و«المزامنة» الحاليين:

**أ. الجرد والاكتشاف**
- اكتشاف تلقائي عبر الوكيل لكل قاعدة موجودة على كل سيرفر (نوعها، حجمها، عدد جداولها، ترميزها) وربطها بالموقع صاحبها عبر رمز `S######`.
- تقرير جاهزية لكل موقع: لديه قاعدة؟ يمكن الوصول إليها؟ حجمها؟ هل يحتاج مساحة إضافية؟

**ب. أفواج التهجير (Migration Waves)**
- التهجير يتم على **أفواج** لا دفعة واحدة: كل فوج مجموعة مواقع (مثلاً 10–20) تُنفَّذ بالتوازي بحد أقصى قابل للضبط.
- لكل موقع مسار من خمس مراحل: **فحص مسبق → نسخة احتياطية → نقل → تحقق → تحويل الاتصال**.
- كل مرحلة تُسجَّل بحالتها ووقتها ومخرجاتها، مع إمكانية إعادة تشغيل مرحلة واحدة دون إعادة الكل.

**ج. الأمان وعدم فقدان البيانات**
- لا تهجير بلا نسخة احتياطية ناجحة أولاً؛ الأصل يبقى كما هو ولا يُحذف نهائياً.
- تحقق بعد النقل: مطابقة عدد الجداول وعدد الصفوف لكل جدول وبصمة بيانات مختصرة؛ أي اختلاف يوقف الفوج تلقائياً.
- **تراجع بضغطة واحدة**: إعادة توجيه الموقع إلى قاعدته الأصلية.
- نافذة تجربة «بلا تنفيذ» (Dry Run) تعرض ما سيحدث بالضبط قبل الموافقة.

**د. الاستعداد للحجم**
- طابور تنفيذ مع حدود تزامن، إعادة محاولة تلقائية عند الفشل العابر، ومهلة زمنية لكل مرحلة.
- لوحة تقدم حيّة: عدد المواقع المكتملة / الجارية / المتعثرة، الوقت المتبقي التقديري، وسجل لكل موقع.
- قوائم المواقع والقواعد تعمل بالصفحات والبحث من الخادم حتى لا تبطؤ مع 240+ سجلاً.
- تصدير تقرير نهائي CSV: الموقع، القاعدة القديمة، القاعدة الجديدة، الحجم، المدة، النتيجة.

## تفاصيل تقنية

- تعديل الملفات القائمة وإضافة صفحات/مكوّنات جديدة عند الحاجة: `src/routes/_authenticated/users.tsx`, `topology.tsx`, `websites.tsx`, `federated.db.tsx` وأقسام `src/components/dbstudio/`.
- إعادة استخدام `src/lib/permissions.ts`, `use-permissions`, `RoleGate` بلا تغيير في الأدوار الأربعة.
- الصلاحيات الدقيقة عبر `site_user_access`, `site_users`, `user_roles`, `server_access` الموجودة.
- العلاقات: توسيع منطق `getEntityRelations` ليشمل كل المواقع دفعة واحدة (`websites`, `site_databases`/`databases`, `servers`, `agent_instances`, `hn_domains`/`ssl_certificates`, `storages`, `site_backups`, `alert_rules`).
- التهجير: دوال خادم جديدة في `src/lib/` (جرد، تخطيط فوج، تنفيذ مرحلة، تحقق، تراجع) تنفَّذ عبر أوامر الوكيل الموقّعة الحالية للقواعد الخارجية، ومباشرةً للقاعدة الداخلية.
- هجرة واحدة (إضافة فقط) لجدولَي **أفواج التهجير** و**مهام التهجير** مع GRANT وسياسات RLS كاملة، وفهارس على الموقع والحالة.
- كل دوال الكتابة محميّة بـ`requireSupabaseAuth` + فحص الدور في `src/lib/roles.server.ts`.

## ضمانات

- يمكن إضافة صفحات جديدة عند الحاجة، ولا حذف لأي جدول أو صف أو بيانات موقع.
- القاعدة الأصلية تبقى سليمة بعد التهجير حتى يؤكد المالك.
- حساب المالك الدائم يبقى محمياً ولا يُعدّل دوره.
